# Maintain rules through human decisions

`ratchet` is the plugin's `bin/ratchet`; fallback: `${CLAUDE_PLUGIN_ROOT}/bin/ratchet`.
Read [the assessment contract](../../docs/DECISION-CARDS.md) for the JSON formats and judgment prompt.
Use the repository's configured coding style and presentation preferences; the bundled style and bullet layout are defaults, not mandatory personal standards. See [customization](../../docs/CUSTOMIZATION.md). Preserve the evidence and approval contract when adapting the question.

1. Reuse the requested review findings. For a new review, delegate to the host's own Code Review skill/tool; do not replace it with a second custom reviewer. On the supported Claude Code path, `ratchet review` invokes that built-in reviewer. For another host, save its original output and import with `ratchet review --from-file FILE --run ID`; do not launch a second reviewer. Honor the existing round cap. Require file, line, summary, failure_scenario, category and severity; retain general correctness findings as unmapped when no rule fits.
2. Run `ratchet decision-context` for the selected full finding IDs. Read the cited code and failure scenarios; use `--location` if a historical line moved. Separate verified observations, model inferences and missing historical evidence. Collect any actual test output needed for the conclusion; do not turn a source hash into proof that a bug exists.
3. Assess every selected finding using the contract: covered, keep, add, rewrite, merge or retire. Group by failure mechanism, not just topic. Write the structured assessment to the task's scratch location. Prefer a brief reason and a scoped clause over a growing list of examples in the rule text.
4. Run `ratchet prepare-decisions --assessment FILE` with the same findings and locations. This saves the context, assessments and proposed edits without changing rules. Use `--parent-batch ID` when reconsidering or revising an earlier batch.
5. By default, format each decision as an action/rule/severity title followed by short, labeled bullet points in this order: source (finding ID, run and original review link), code (linked absolute path and lines, snapshot/current), rule coverage, failure scenario, evidence, reason, exact clause/diff, scope/target. Keep one subject per bullet with a blank line between items; let long content wrap naturally. Link short filenames to absolute paths when supported; otherwise show the paths. Retain exact proposed text and material uncertainty. Use tool-supplied locations, never invented ones. Keep hashes, full logs and long excerpts in the saved batch.
6. Put that brief inside the host's native user-question tool, such as AskUserQuestion, with accept, adjust, reject or defer choices; do not reduce the question to IDs or assume the human saw earlier chat output. Split unrelated proposals when needed to preserve key evidence. Adapt to the host's supported choice count and use free text or a follow-up for adjustment. If no native question tool exists, ask in chat. Do not build a custom UI or require the human to copy JSON. A default, silence, model recommendation or preview-widget state is not an answer.
7. Translate only actual human responses into the answer contract; retain the response text. A merge is one decision for all its changes. Group covered/keep summaries for convenience while recording each group's actual decision. For adjust, record `revise`, prepare the requested replacement, and ask again about its final text. Do not apply an unreviewed rewrite.
8. Run `ratchet apply-decisions --input FILE`, then `ratchet compile --check --strict`. Report the actual edits and the saved batch/receipt. Accepted rules do not close code findings; code fixes and finding outcomes remain separate. Stop after this batch, or at an explicit deferred decision. Never auto-retire rules or escalate the review cap.

Run `ratchet decision-summary` to report acceptance, revision requests, rejection and deferral as facts. Initial suggestions and revisions are counted separately; keep/no-change groups are separate from change proposals. No consistency score,
benchmark result, cross-project synchronization, commit or push is implied by this workflow.
