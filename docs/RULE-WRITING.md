# Write rules that can be applied and traced

The coding-style file is an instruction document for both code authors and reviewers.
The bundled template demonstrates one author's priorities; reuse its structure while
choosing your own standards. A rule should answer: when does it apply, what is required,
what failure does it prevent, and what is allowed?

## A compact clause blueprint

```markdown
## REL · State replacement

- **[REL.1]** Preserve usable state until its replacement is prepared and validated; restore usable state if replacement fails. (should-fix)
  Scope: replacing an installed tool or configuration that has an existing usable copy.
  Exception: disposable temporary artifacts that can be rebuilt.
  Failure: copying fails after the old usable copy has been deleted.
  Violates: delete the installed copy, then start copying its replacement.
  Complies: prepare and validate a replacement before switching, with recovery on failure.
```

This example is a writing pattern, not an instruction to add REL.1 everywhere.
Put the ID, core obligation and severity on the definition line. Supporting scope,
exceptions and examples can follow it. If the generated short form loses a necessary
qualification, provide an inline `<!-- digest: ... -->` on the definition line and
check the actual compiled result. Digest overrides are maintained text, not summaries
generated by a model.

Use a stable ID for a stable concept. Rewording it should not give the same concept
a new identity; a different requirement needs a different ID. Keep evidence of why
the wording changed in proposal history. Do not inflate the rule body with every
incident, path or review transcript. A rule and the evidence supporting its adoption
serve different reading needs.

## Risk, scope and examples

Severity describes the consequence and urgency under this project's policy. It does
not decide whether a finding deserves a new rule. First test whether existing rules
already cover the mechanism and whether the observation generalizes beyond one bug.
Mechanical enforcement, reviewer judgment and deferred cleanup are separate concerns.

Examples are optional. Add a violating/compliant pair when a boundary is easy to
misread, especially an exception. An example should differ in the relevant behavior,
not merely variable names. Keep examples beside the full clause or in a linked fixture;
do not put every example into the session digest. These examples provide context for
the reviewer; they are not executed tests unless a separate test actually runs them.

## Phrasing and the digest budget

- **Prefer "Don't …" where the rule can be a prohibition.** "Don't wrap more than the
  one line expected to fail in `try`" is easier to check than "Keep the guarded block
  small", and it names the failure. Zhang et al. (2026),
  ["Guardrails Beat Guidance"](https://arxiv.org/abs/2604.11088), studied rule files
  for coding agents and found that every individually helpful rule was a prohibition.
  The study measured task resolution, not style compliance, so take it as a reason to
  try the phrasing, not as evidence that it improves reviews in your repository. A
  requirement with no clean negation (a required step, an ordering) stays positive.
- **Merge or retire before you add.** The digest has a byte budget (`digest_max_bytes`,
  default 4096) and the whole digest is loaded into every session. `ratchet compile`
  only warns when it is over budget, but a proposal that would push it over is refused
  when it is prepared or applied. When the budget is nearly full, first look for two
  clauses that can become one, or one that no longer applies, and propose that change
  before the addition.

## What the current implementation retrieves

There are three different mechanisms today:

1. `rules.py` parses definitions into an ID-to-clause dictionary, carrying text,
   definition line and severity. Exact ID lookup is available to the tool.
2. `compile` deterministically produces a short digest for context injection. It is
   not a semantic search or retrieval pipeline. It uses definition lines and optional
   digest overrides, rather than automatically understanding supporting paragraphs.
3. `decision-context` supplies the configured rule texts and selected finding evidence.
   The model compares them; a validated assessment attaches the matched clause blocks
   and source locations. That comparison currently reads the supplied corpus, rather
   than retrieving only a ranked subset.

Stable IDs therefore help traceability and exact lookup, but do not by themselves
prove retrieval quality or make this a RAG system. There is no embedding index or
measured retrieval-efficiency claim in this implementation. Before adding retrieval,
measure whether the corpus is too large or relevant clauses are being missed. A future
retriever must retain scope, exceptions, linked rules and version information with
each clause; finding the ID alone is insufficient.

## Check an edit

- Compile the digest and check the size budget; inspect the text the reviewer will receive.
- Confirm that the short form preserves the obligation and material exceptions.
- Use a failing and a compliant example to test an ambiguous rule's boundary.
- Preserve finding → proposal → human decision → rule revision provenance.
- Keep general correctness findings as `unmapped` when no local style rule applies.

Changing a rule can improve clarity without improving review accuracy. Demonstrate
the specific behavior tested, and leave broader effectiveness claims to later evaluation.
