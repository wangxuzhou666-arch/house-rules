# Compile reference

`ratchet compile` turns your rules files into a short digest that an agent loads as context, so a reviewer (or a coding session) judges code against the same clause ids the ledger records. It is deterministic text processing: no model is involved, and the same rules always give the same bytes.

## Adopt it in one line

1. Point the config at the rules (`.ratchet.json`):

   ```json
   { "rules_files": ["docs/CODING-STYLE.md"] }
   ```

2. Run `ratchet compile`. It writes `CODING-STYLE.digest.md` at the repo root.
3. Add this line to the repo's `CLAUDE.md`:

   ```
   @CODING-STYLE.digest.md
   ```

Claude Code expands `@path` imports in `CLAUDE.md`, and the built-in `/code-review` only reads `CLAUDE.md`, so the one line gives both coding sessions and the review the digest. Commit the digest; re-run `ratchet compile` whenever the rules change (see [check mode](#check-mode) for keeping it fresh automatically).

## What the digest contains

```
<!-- generated by ratchet compile from docs/CODING-STYLE.md@0123456789ab; do not edit by hand -->
# Style digest

## Violations
P0E.1 | blocker | Keep the guarded `try` block to the one line expected to fail
P1.1 | should-fix | Nesting depth of five or more is a violation
P3.1 | nice | Explain why, not what

## Reviewer rules
R.1 | Standards come from this file, not from the reviewer

## Labeling
...
```

- **Header**: a single comment naming every rules file, relative to the repo root, with the first 12 hex digits of the sha256 of its bytes. Edit a source and its hash changes, so a stale digest is visible at a glance.
- **Violations**: `ID | severity | short rule` for every clause that has a severity (see below), in rules-file order.
- **Reviewer rules**: `ID | short rule` for the clauses that have none: guidance about how to review, not code defects.
- **Labeling**: fixed text telling the reporter to set `category` to the violated clause id in kebab-case (`P0E.6` becomes `p0e-6`, which is what `ingest-code-review` reads) and `severity` to the one listed under Violations; to use `unmapped` rather than stretch a clause to fit; and to file one finding per defect, naming other matching ids in the summary.

A section with no lines shows `(none)`.

## Severity table

Severity is declared once, per clause family, in a markdown table anywhere in a rules file:

```
| family | severity |
|---|---|
| P0E, P0F | blocker |
| P1, P2 | should-fix |
| P3 | nice |
```

- Exactly two columns. Header cells are matched case-insensitively (`Family`, `SEVERITY` work). The separator row is required.
- A family is the part of a clause id before the dot (`P0E.6` is in family `P0E`). Matching is exact: `P0` does not cover `P0E.6`.
- Severities are `blocker`, `should-fix` and `nice`. Anything else is an error, as is a row with a different number of cells.
- A family that is not in the table is a **reviewer-guidance family**: its clauses have no severity and are listed under Reviewer rules.
- A severity tag on a clause's own line (`(blocker)`, `` `nice` ``, see [LEDGER.md](LEDGER.md#rules-files)) is more specific than the table and wins; such a clause is listed under Violations.
- A table inside a code fence is ignored. With no table at all, nothing has a severity: compile still works, warns on stderr, and lists everything under Reviewer rules.

The table is also the default severity for `ingest-code-review` and `add`: when a reported finding has no usable severity, the severity of its clause comes from the clause tag or the table, else `should-fix`.

## Layering

`rules_files` is ordered, global first and the project layer last:

```json
{ "rules_files": ["../shared/CODING-STYLE.md", "docs/CODING-STYLE.md"] }
```

A later file may **add** clauses and table rows. It may not redefine a clause id, nor give a family a different severity than an earlier table did: both are errors that name both places. Append, never override. Equal rows repeated in a later file are fine. Table rows from all files are merged, so a project file can give its own new families a severity.

## Short rule

The text of a clause line after its id, reduced deterministically:

1. Severity tags and HTML comments are removed; whitespace is collapsed.
2. `**` bold markers are removed; backticks are kept.
3. The text is cut at the first sentence end: the CJK full stop (U+3002), the CJK semicolon (U+FF1B), or `.` / `;` followed by whitespace or the end of the text. (`os.path` and `1.5` are not cut.) A sentence end inside an open bracket pair does not count, so a parenthetical is never cut in half. Tracked pairs: `()`, `[]` and the full-width parentheses (U+FF08/U+FF09), lenticular brackets (U+3010/U+3011) and corner brackets (U+300C/U+300D); nesting is followed. If a bracket is never closed, the text is not cut at all.
4. Trailing whitespace, `:` and the full-width colon (U+FF1A) are removed. A clause line that ends in a colon introducing sub-bullets (which the digest does not carry) would otherwise end mid-sentence.
5. If it is longer than `digest_max_chars` characters (default 90; characters, not bytes), it is cut to `digest_max_chars - 1` characters plus an ellipsis character (U+2026), so the result is never longer than the cap. The cap may land inside a bracket; the ellipsis marks the truncation.

Only the clause's own line is read, never the lines after it. For a table-row clause (`| P2.3 | should-fix | text |`) the text is the cells after the id, minus a severity cell.

### Override comment

When the automatic cut reads badly, put the wording you want on the clause line:

```
1. **[P0E.5]** Log inside `except` with `logger.exception` (the other form drops the traceback; see ruff TRY400). <!-- digest: Use `logger.exception` in `except`, not `logger.error` -->
```

The text of `<!-- digest: ... -->` is used verbatim: not cut, not capped, not stripped of markers. A clause with no text on its line and no override is an error.

## Injection

To put the same sections inside an existing file (for example a `CLAUDE.md` that cannot use an `@import`), list the file and add a pair of markers where the block belongs:

```json
{ "inject_targets": ["CLAUDE.md"] }
```

```
<!-- style-digest:begin -->
<!-- style-digest:end -->
```

Compile replaces everything between the markers with a one-line source comment followed by the Violations, Reviewer rules and Labeling sections (no title line, so it nests under your own headings). Text outside the markers is never touched. Each marker must appear exactly once and the begin marker must come first; a missing, duplicated or reversed marker, or a target that does not exist, is an error. Compile validates every target before it writes anything, so one bad target leaves all files, the digest included, as they were.

## Check mode

`ratchet compile --check` writes nothing. It exits 1 and lists every stale output (the digest or an injected block that differs from what compile would write, or a digest that does not exist yet) on stderr, and exits 0 when all are fresh:

```
stale: CODING-STYLE.digest.md (digest, out of date)
stale: CLAUDE.md (injected block, out of date)
run `ratchet compile` to regenerate
```

Use it in a pre-commit hook or CI to catch a rules edit committed without its regenerated digest. Hand edits inside an injected block, or to the digest, count as stale; edits outside the markers do not.

`ratchet compile --dry-run` prints a unified diff of what a real run would change and writes nothing. Both modes still run every validation.

## Size budget

`digest_max_bytes` (default 4096, measured in UTF-8 bytes of the digest file) is a budget, not a hard limit: going over prints a warning on stderr and the digest is still written. With `--strict` the command then exits 1, so CI can enforce it. Text in languages with multi-byte characters costs about three bytes per character; lower `digest_max_chars` or add override comments if the digest runs over.

## Config keys

| key | default | meaning |
|---|---|---|
| `digest` | `CODING-STYLE.digest.md` | digest output path, relative to the repo root |
| `digest_max_chars` | `90` | cap for one short rule, in characters (positive integer) |
| `digest_max_bytes` | `4096` | size budget for the digest, in bytes (positive integer) |
| `inject_targets` | `[]` | files that carry a `style-digest` marker pair to fill |

`rules_files` and `clause_id_pattern` (see [LEDGER.md](LEDGER.md#config-ratchetjson)) decide which clauses exist.

## Exit status

`0` success (and `--check` with nothing stale); `1` for any error, for `--check` with stale outputs, and for `--strict` when the digest is over budget.
