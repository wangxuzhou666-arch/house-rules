# 编写可执行、可追溯的规则

编码规范文件是一份同时写给代码作者和 reviewer 的指令文档。内置模板展示的是作者本人的优先级；你可以沿用它的结构，但标准要自己定。一条规则应该回答四个问题：什么时候适用，要求什么，防止什么失败，什么情况下允许。

## 一个紧凑的条款蓝本

```markdown
## REL · 状态替换

- **[REL.1]** 在替换物准备好并通过校验之前，保留现有可用的状态；替换失败时恢复可用状态。 (should-fix)
  适用范围：替换已有可用副本的已安装工具或配置。
  例外：可丢弃、可重建的临时产物。
  失败场景：旧的可用副本已被删除，复制新副本时失败。
  违规写法：先删除已安装的副本，再开始复制它的替换物。
  合规写法：切换之前先准备并校验替换物，失败时可恢复。
```

这个示例是一种写法，不是让你处处都加 REL.1。把 ID、核心义务和严重度放在定义行上；适用范围、例外和示例可以跟在后面。如果自动生成的短句丢掉了必要的限定条件，就在定义行上加一个行内的 `<!-- digest: ... -->`，并检查实际编译出来的结果。digest 覆盖文本是人维护的文字，不是模型生成的摘要。

同一个概念用稳定的 ID。改写措辞不应该让同一个概念换一个身份；要求不同，就用不同的 ID。措辞为什么改，把证据留在提案历史里。不要把每次事故、每个路径、每份 review 记录都塞进规则正文。规则本身，和支撑它被采纳的证据，面向的是不同的阅读需求。

## 风险、范围与示例

严重度描述的是：在本项目的政策下，后果有多严重、多紧迫。它不决定一条发现值不值得催生新规则。先检验现有规则是否已经覆盖了这个机制，以及这个观察能不能推广到单个 bug 之外。机械强制、reviewer 判断和延后清理是三件不同的事。

示例是可选的。当边界容易被读错时，尤其是例外情形，补一对违规/合规示例。示例应当在相关行为上有差别，而不只是变量名不同。示例放在完整条款旁边，或放在被链接的 fixture 里；不要把每个示例都塞进会话 digest。这些示例是给 reviewer 的上下文；除非另有测试真的去运行它们，否则它们不是被执行的测试。

## 措辞与 digest 预算

- **能写成禁止的，就写成「不要……」。** 「不要在 `try` 里包住超过那一行预期会失败的代码」比「让被保护的块保持小」更容易检查，也直接点出了失败是什么。Zhang 等人（2026）的[「Guardrails Beat Guidance」](https://arxiv.org/abs/2604.11088)研究了面向编码 agent 的规则文件，发现每一条单独看有帮助的规则都是禁止型的。这项研究度量的是任务解决率，不是风格合规，所以把它当作值得一试的措辞依据，而不是「在你的仓库里一定能提高 review 质量」的证据。没有干净的否定写法的要求（必须执行的步骤、先后顺序）仍然写成肯定句。
- **先合并或退役，再新增。** digest 有字节预算（`digest_max_bytes`，默认 4096），整份 digest 会加载进每个会话。`house-rules compile` 超预算时只会警告，但会让 digest 超预算的提案，在准备或应用时会被拒绝。预算快满时，先找两条可以并成一条的条款，或一条已经不再适用的条款，把这个改动排在新增之前提出。

## 当前实现是怎么检索的

目前有三种不同的机制：

1. `rules.py` 把定义解析成「ID 到条款」的字典，带上正文、定义行和严重度。工具可以按 ID 精确查找。
2. `compile` 确定性地生成一份简短的 digest，用于注入上下文。它不是语义搜索，也不是检索流水线。它使用定义行和可选的 digest 覆盖文本，不会自动理解定义行后面的补充段落。
3. `decision-context` 提供已配置的规则文本和选定发现的证据。由模型做比对；经过校验的评估会附上匹配到的条款块和源码位置。这个比对目前读取的是提供的整个语料，而不是只检索一个排好序的子集。

因此，稳定的 ID 有助于追溯和精确查找，但它本身既不能证明检索质量，也不会让这套东西变成 RAG 系统。这个实现里没有 embedding 索引，也没有经过度量的检索效率声明。加检索之前，先度量：语料是不是太大了，相关条款是不是被漏掉了。将来的检索器必须让每条条款带着它的范围、例外、关联规则和版本信息；只找到 ID 是不够的。

## 检查一次编辑

- 编译 digest 并检查体积预算；看一遍 reviewer 将收到的文本。
- 确认短句保留了义务和重要的例外。
- 用一个违规示例和一个合规示例测试有歧义的规则的边界。
- 保留「发现、提案、人的决定、规则修订」这条来源链。
- 没有适用的本地风格规则时，把通用的正确性发现保持为 `unmapped`。

改一条规则可以让它更清晰，却不一定让 review 更准。只证明你实际测过的那个行为，更宽泛的有效性结论留给以后的评估。
