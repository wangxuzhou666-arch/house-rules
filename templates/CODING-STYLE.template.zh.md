# 编码规范（DRAFT 模板）

<!-- ADJUST: 这是一个起点，不是标准。下面每一个可调的旋钮都标了 ADJUST。把阈值、工具代码和示例改成你的仓库真正强制执行的内容，并删掉你不打算要求别人遵守的条款。改完后运行 `house-rules compile` 重新生成 digest。 -->

> 读者：写代码的工程师和编码 agent，以及评判代码的 reviewer（人或模型）。
> 角色：评审标准的唯一事实来源。reviewer 不自己发明阈值，阈值都写在这里。
> 分层：跨项目通用的规则放在这个文件里，项目特有的规则（技术栈的坑、已知债务）放在第二个规则文件里，并在 `rules_files` 中排在这个文件之后。后面的文件只能新增条款，不能覆盖。
> 针对的问题：生成代码容易产生的四类冗余：吞掉错误的宽泛 catch、把失败伪装成正常的兜底、只有一个实现的抽象，以及复述代码的注释。

## 0. 执行层级

<!-- ADJUST: 把机械层里用到的工具换成你的仓库真正在用的。 -->

| 层级 | 谁来跑 | 何时跑 | 覆盖什么 |
|---|---|---|---|
| 机械层 | linter 加一个小的语法树脚本，挂在 pre-commit | 每次提交，只看暂存的行 | 凡是能由规则代码或语法树判定的 |
| 判断层 | reviewer | 每个 diff | 凡是需要结合上下文才能判断的 |
| 存量层 | 定期审计 | 每个批次或里程碑 | 历史债务，批量清理；绝不放进 pre-commit，否则它天天红，最后被人绕过 |

一条规则归哪一层：如果它在每个会话里都成立、与当前任务无关、且没有歧义，就做成机械层；否则归判断层。

<!-- ADJUST: 条款族列表。在这里和 R.4 下面的严重度表里同步增删族。 -->
条款 ID：`P0E.n` 异常，`P0F.n` 回退，`P1.n` 复杂度，`P2.n` 抽象，`P3.n` 注释，`R.n` reviewer 行为准则。linter 报出、但不匹配任何条款的问题，记作 `<tool>:<code>`。

## P0 · 异常：缩小受保护的代码块，给每个宽泛 catch 一个身份

**为什么**：`try` 越宽，越多种不同的失败被塞进同一个处理分支。超时（该重试）、缺 key（是 bug）、写入失败（该告警）变成同一行日志，后面再跟一句 `return None`，失败看起来就像成功。

1. **[P0E.1]** `try` 里只放你预期会失败的那一行；其余的挪到块后面。 <!-- ADJUST: 对应语言的工具代码，例如 ruff TRY300 会标出 try 里的 return。 -->
2. **[P0E.2]** 捕获具体的异常类型，并给每种类型各自的处理动作。所有类型都走同一种响应，是在压制，不是在处理。
3. **[P0E.3]** 只有下列情形允许使用兜底式（catch-all）handler，并且该行必须写明属于哪一种以及理由。 <!-- digest: catch-all 只用于：旁路、可选附加信息、批处理隔离、顶层处理器、带 cause 重抛；并在该行写明属于哪一种 --> <!-- ADJUST: 合法情形的白名单。可以缩短或扩充，并同步修改 digest 注释。 -->
   - **旁路（side channel）**：脱敏、指标或遥测不能拖垮主流程。
   - **可选附加信息**：结论并不依赖的字段（比如把 usage 计数记为 0）。
   - **批处理隔离**：一条坏数据不能拖垮整批；要记录这条数据的身份。
   - **顶层处理器**：服务或 worker 的最外层，记录完整的 traceback，让进程活下去。
   - **带 cause 重抛**：重试包装器抛出最后一次的错误，或边界层把解析失败翻译成客户端错误、并把原始异常保留为 cause。判据是异常的身份没有丢。能收窄类型的地方就收窄类型。
4. **[P0E.4]** 宽泛 catch 上的裸 lint 抑制不被接受；必须写明情形和理由。 <!-- ADJUST: 例如 ruff 里不带说明的 `noqa: BLE001`，或不带描述的 eslint-disable。 -->
5. **[P0E.5]** 在 handler 里记日志，要用能保留堆栈的调用，不用会丢堆栈的那个。 <!-- ADJUST: 例如用 `logger.exception` 而不是 `logger.error`（ruff TRY400）；`console.error(err)` 要传 error 对象。 -->
6. **[P0E.6]** 用显式的抑制写法替换空 handler，并写明异常类型。 <!-- ADJUST: 例如 `contextlib.suppress(KeyError)`（ruff SIM105）。 -->

## P0 · 回退：失败不能冒充成功

**为什么**：`return None`、`or default`，以及永远不会执行的 `else`，会把「出了问题」改写成「看起来没事」。它是宽泛 catch 的另一半：一个丢掉信息，另一个把「信息已经丢了」这件事藏起来。

1. **[P0F.1]** 快速失败：程序员错误用 assert，输入只在边界校验。 <!-- ADJUST: 边界指你的请求处理入口、配置解析和外部数据入口。 -->
2. **[P0F.2]** 显式降级：要记日志并写明回退值，绝不静默返回 `None`。
3. **[P0F.3]** 不要过度防护：对一百次才失败一次的情况，不加防御分支。
4. **[P0F.4]** 只在值确实可能为空的地方判空；信任类型标注。

## P1 · 复杂度：看嵌套深度，不看行数

**为什么**：读代码意味着在工作记忆里记住「我现在处在哪些条件之内」，而工作记忆大约只装得下四个组块。深度为 N 时，最内层那一行要同时满足 N 个条件。一个很长但很平的函数（一排互不相干的 if）只是长，并不复杂。

1. **[P1.1]** 嵌套深度达到 5 层或以上即违规。修法按顺序：卫语句、提取内层代码块、分派表。 <!-- ADJUST: 深度阈值。按 if / for / while / try / with 的层数计算。 -->
2. **[P1.2]** 仅作提示：超过 50 行且圈复杂度超过 15 的函数值得看一眼。数据密集型函数除外。(nice) <!-- ADJUST: 两个阈值，以及所用的工具（例如 ruff C901）。除非你的仓库数据表明长度能预测缺陷，否则保持为仅作提示。 -->
3. **[P1.3]** 会赋值或 return 的分支必须有 `else`，卫语句除外。

元规则：代理指标不能跨领域迁移。采用某个阈值之前，先在你自己的仓库里验证。

## P2 · 抽象：只有一个实现，那只是个包装

**为什么**：抽象的价值在于统一已经存在的多个实现。只有一个实现时，它统一的是想象中的未来，白白多出一层间接。

1. **[P2.1]** 基类、protocol 或工厂至少要有两个真实的实现。
2. **[P2.2]** 第三次重复时再抽象，绝不为假想的未来需求去抽象。
3. **[P2.3]** 一次性的需求不建配置层、插件系统或注册表。
4. **[P2.4]** 泛名要加限定词：`data`、`result`、`info`、`tmp`、`manager`、`handler`、`util`。 <!-- ADJUST: 你自己的禁用名单。 -->
5. **[P2.5]** 对称的词对要对称命名（`start`/`stop`、`open`/`close`、`send`/`recv`）。 <!-- ADJUST: 布尔值命名属于判断，不是机械规则。读起来像名词或动词的布尔名（`timeout`、`write`）应改成 `should_timeout` 或 `is_write_mode`；对 `dry_run`、`force`、`truncated` 这类惯用名，不要硬性要求加前缀。 -->

## P3 · 注释：写为什么，不写是什么

**为什么**：代码本身已经说明了它做什么。再复述一遍只是噪音，会淹没真正重要的注释：为什么选这个而不是另一个、有什么坑、实测的数字是多少。

1. **[P3.1]** 不写复述代码或函数名的注释。
2. **[P3.2]** 注释那些不显然的东西：一个决策、一个坑、一个顺序约束。
3. **[P3.3]** 注释使用项目约定的语言。 <!-- ADJUST: 选定一种。 -->
4. **[P3.4]** 提交里不留调试残留：游离的 print、临时 TODO、被注释掉的代码。

## R · Reviewer 行为准则

1. **[R.1]** 标准来自这个文件，而不是 reviewer 本人。如果没有适用的条款，就写「没有对应标准，建议 X」，不要报成违规。
2. **[R.2]** 不许橡皮图章：如果没发现问题，要说明这段代码做对了哪条规则。
3. **[R.3]** 要教：每条发现都要写明机制和修法，不能只说症状。
4. **[R.4]** 严重度跟随被违反条款所属的族。 <!-- ADJUST: 族到严重度的对照表。不在表里的族是指导性条款，其条款不带严重度。表头的 `family` 和 `severity` 必须保持英文，解析器按这两个词识别这张表。 -->

   | family | severity |
   |---|---|
   | P0E, P0F | blocker |
   | P1, P2 | should-fix |
   | P3 | nice |

5. **[R.5]** 生成代码的特征，归到对应的 P 条款下报告：整段代码包一个大 try、对不可能为 null 的值做 null 检查、只有一个实现的基类、复述名字的 docstring、「以防万一」的默认值、与本仓库风格格格不入的样板代码。 <!-- digest: 生成代码的特征，归到对应的 P 条款下报告：一个大 try、多余的 null 检查、单实现基类、复述型 docstring、「以防万一」的默认值 -->
6. **[R.6]** 评判改动之前，先读周围的代码。孤立地看是错的东西，放进系统的不变量里可能是对的。
7. **[R.7]** 新增 gate 或规则，需要一个能证明它会触发的失败示例。 <!-- ADJUST: 如果你不写自己的 lint gate，可以删掉这一条。 -->
   一个跑绿的 gate 什么也证明不了，因为永远返回绿的 gate 同样是绿的。证明的办法，是亲手构造出它应该抓到的东西，看它变红。每条规则至少给一个正例（必须失败）和一个反例（必须通过），先从规则明文列出的例外情形写起，因为日后收紧规则时，最先被弄坏的就是这些。退回旧行为必须让它重新变绿，这样才能确认红色是新增的那一部分造成的。每个正例都要绑定到实际触发它的那条规则。有多条规则时，把它们逐条关掉，确认只有被关掉那条规则对应的示例变绿。把测试提交进仓库；一次性的手工运行，日后什么也证明不了。
